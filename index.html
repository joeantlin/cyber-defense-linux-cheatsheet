▶ls— list files and directories
Definition

Lists the contents of a directory. With no argument, lists the current working directory.

Use Case (Cyber Defense context)

First command run in almost any directory to see what's there — including hidden files that might be a dropped payload or persistence mechanism.

Syntax

Relevant Options
FlagWhat it does

-aShow all files, including hidden dotfiles
-tSort by modification time, newest first
-SSort by file size, largest first
-iShow inode numbers
-RRecursive listing through subdirectories
Examples
# Detailed listing including hidden files
$ ls -la user1/Downloads

# What changed most recently in this directory?
$ ls -lat

# Find unusually large files
$ ls -laS

▶cd— change directory
Definition

Changes the shell's current working directory — where you "are" in the filesystem for every command that follows, until you cd again. Accepts absolute paths (start with /), relative paths, ./.., or ~ for the home directory.

Use Case

One of the very first commands anyone learns, since almost everything else in a terminal depends on being in the right place first — running a script, editing a config, or checking a log all assume you're already where you need to be. Getting comfortable moving around quickly (especially cd -, below) pays off constantly.

Syntax
$ cd [path]
Examples
# Absolute path — always starts from the filesystem root
$ cd /home/user1/Desktop/

# Relative path — starts from wherever you already are
$ cd Desktop/notes

# Up one level to the parent directory
$ cd ..

# Up two levels at once
$ cd ../..

# Home directory shortcut
$ cd ~/Downloads

# No argument at all — jumps straight home, same as cd ~
$ cd

# Jump back to whichever directory you were in immediately before —
# the fast way to move back and forth between two places
$ cd -
Notes

. = current directory, .. = parent directory, ~ = home directory. Root user's home is /root, not to be confused with / (filesystem root). cd is a shell builtin, not a separate program on disk — it has to be, since a standalone program can't change the shell's own working directory once it exits. That's also why cd inside a script only affects that script's subshell, not the terminal you ran it from.

See Also
pwd, ls, find

File Forensics & Integrity
▶find— locate files by name, permission, owner, or age
Definition

Searches a directory tree for files matching criteria — name, permission bits, owner, modification time, and more. Far more powerful than ls for hunting across a whole filesystem.

Use Case (Cyber Defense context)

One of the highest-value hunting commands available: surface SUID/SGID binaries (a privilege-escalation favorite), orphaned files, world-writable files, or anything modified recently — all classic signs of tampering.

Syntax
$ find <path> [criteria]
Relevant Options
FlagWhat it does
-perm -4000Find files with the SUID bit set
-perm -2000Find files with the SGID bit set
-nouser / -nogroupFind files owned by a UID/GID that no longer exists
-mtime -nModified within the last n days
-newer fileModified more recently than a reference file
-perm -o+wFind world-writable files
-type f / -type dRestrict to files or directories
Examples
# Find every SUID binary on the system
$ find / -perm -4000 -type f 2>/dev/null

# Files modified in the last 24 hours
$ find / -mtime -1 -type f 2>/dev/null

# Orphaned files (owner no longer exists — often a leftover from a removed account)
$ find / -nouser -o -nogroup 2>/dev/null

# World-writable files — anyone can modify these
$ find / -perm -o+w -type f 2>/dev/null
See Also
stat, chmod

Text Processing & Search
▶grep— search text using patterns
Definition

grep (Global Regular Expression Print) scans input line-by-line and prints any line that matches a given pattern or string. Reads from a file argument, multiple files, or STDIN — commonly used at the end of a pipe chain.

Use Case (Cyber Defense context)

Primary tool for hunting during initial triage: pulling suspicious lines out of logs, finding accounts with shell access in /etc/passwd, searching config files for a setting, or filtering the output of another command down to what matters. Combine with awk/sed for full log-hunting pipelines.

Syntax
$ grep [options] "pattern" <file>
# or, from a pipe:
$ cat <file> | grep "pattern"
Relevant Options
FlagWhat it does
-iCase-insensitive match
-r / -RRecursive search through a directory
-vInvert match — show lines that don't match
-EExtended regex (enables |, +, {} without escaping)
-nShow line numbers with matches
-cCount matching lines instead of printing them
-lPrint only filenames that contain a match
--colorHighlight matched text in output
-wMatch whole words only
-A n / -B n / -C nShow n lines of context after / before / around a match
-oPrint only the matched portion of the line, not the whole line
-f fileRead patterns to search for from a file — good for matching a list of known-bad IPs or strings
Examples
# Find all users with a bash or sh shell in /etc/passwd
$ cat /etc/passwd | grep -E ':(/bin/(bash|sh))$'

# Search recursively for a string across config files
$ grep -r "PermitRootLogin" /etc/ssh/

# Case-insensitive search with line numbers
$ grep -in "error" /var/log/auth.log

# Read a failed-login hit with 3 lines of context on each side
$ grep -A3 -B3 "Failed password" /var/log/auth.log

# Match a list of known-bad indicators against a log
$ grep -f iocs.txt /var/log/syslog

# Chained: list usernames that have a real login shell
$ cat /etc/passwd | grep -E ':(/bin/(bash|sh))$' | awk -F ':' '{print $1}' > users
See Also
sed, awk, redirection & pipes, Regex Quick Reference

▶awk— field-based text filtering and scripting
Definition

Processes text a line at a time and splits each line into fields (like columns), so you can select, filter, or transform specific fields. Effectively runs a small program over each line of input.

Use Case (Cyber Defense context)

Extracting one column out of structured output — usernames from /etc/passwd, a specific field from a CSV log, or a PID from ps output.

Syntax

Examples

# accounts and excluding system/service accounts
$ awk -F ':' '$3 >= 1000 {print $1}' /etc/passwd

▶< > >> |— I/O redirection & pipes
Definition

Every command has three data streams: STDIN (input it reads), STDOUT (normal output), and STDERR (error output, kept separate from STDOUT on purpose). Redirection sends any of these to a file instead of the screen; a pipe sends one command's STDOUT straight into the next command's STDIN, without a file in between at all.

Use Case (Cyber Defense context)

This is how most real investigation one-liners are built: cat a file, pipe it through grep to filter, pipe that through awk to extract a field, then redirect the result into a file for later reference. Knowing the difference between > and >> also matters constantly — one destroys what was there, the other doesn't.

Syntax
$ command < input_file
$ command > output_file
$ command >> output_file
$ command1 | command2
Relevant Operators
OperatorWhat it does
<STDIN — feed a file in as input
>STDOUT, overwrite — creates the file if it doesn't exist, replaces its entire contents if it does
>>STDOUT, append — adds to the end of the file instead of replacing it
2>STDERR only — redirect just the error output, leaving normal output on screen
>> file 2>&1Redirect both STDOUT and STDERR to the same file, appending
|Pipe — send one command's STDOUT directly into the next command's STDIN
Examples
# STDIN: feed a file in as input instead of typing/piping
$ sort < unsorted_names.txt

# STDOUT, overwrite: creates or replaces the file entirely
$ ss -tulnp > open_ports.txt

# STDOUT, append: adds a new entry without erasing prior ones —
# use this for anything you're building up over time, like a log
$ echo "$(date): checked open ports" >> investigation_log.txt

# STDERR only: capture just the errors, useful when scanning
# many hosts and you only care about what failed
$ ping -c 1 10.0.0.5 2> ping_errors.txt

# Capture everything — output and errors — into one log
$ ./scan_script.sh >> full_run.log 2>&1

# Chained pipe: break it down at each | and reason through
# one segment at a time
$ cat /etc/passwd | grep -E ':(/bin/(bash|sh))$' | awk -F ':' '{print $1}' > users
Caution

> overwrites silently — no warning, no confirmation. Pointing it at a file you meant to keep (a config, a log, someone else's work) destroys the original contents instantly. If you're not sure whether a file already has something worth keeping, use >> or check first.

See Also
grep, awk, tail
Permissions & Ownership
▶chmod— change file permissions⚠ risk
Definition

Changes read/write/execute permissions on a file or directory, either symbolically (rwx) or numerically (octal, e.g. 744). See the Reference section for how octal maps to rwx.

Syntax
$ chmod <mode> <file>
Relevant Options
FlagWhat it does
-RApply recursively to a directory and everything inside it
--reference=fileCopy the mode from another file instead of typing octal
Examples
# rwxr--r-- 
$ chmod 744 script.sh

# r-x-w---x
$ chmod 755 script.sh
Caution

Overly permissive modes (777) can open up a system unintentionally — set only what's needed. -R is especially dangerous: it applies to every file underneath, including ones that needed a different, more restrictive mode. Spot-check a directory tree before running it recursively.

See Also
chown, chattr
▶chown— change file owner/group
Definition

Changes which user and/or group owns a file.

Syntax
$ chown user:group <file>
Examples
$ chown user1:group1 notes.txt
$ chown root:root notes.txt
Caution

Ownership backs the permission model — handing a file to the wrong owner can grant access you didn't intend, even without touching its permission bits. Worth a second look whenever ownership on a sensitive file changes unexpectedly.

See Also
chmod
▶chattr— set/unset the immutable attribute⚠ risk
Definition

Changes low-level filesystem attributes on a file. The most relevant one for defense is the immutable bit (i) — while set, the file can't be modified, deleted, or renamed by anyone, including root, until it's unset.

Use Case (Cyber Defense context)

Lock down a critical config file so it can't be silently overwritten by an attacker (or a script) — even with root access, the immutable bit has to be removed first.

Syntax
$ chattr +i <file>   # make immutable
$ chattr -i <file>   # remove immutable bit
Caution

If you set +i and forget, future legitimate edits (including automated ones) will silently fail. Check with lsattr before troubleshooting a file that "won't save." Also depends on filesystem support, not distro directly — ext2/3/4, btrfs, and xfs all support the immutable bit, but some network or specialty filesystems don't.

See Also
lsattr
▶lsattr— list file attributes
Definition

Displays the filesystem attributes on a file, including whether the immutable bit is set.

Syntax
$ lsattr <file>
Examples
# Check whether the immutable bit is set before troubleshooting

▶usermod— modify an existing user's settings⚠ risk
Definition

Changes an existing user's settings — groups, shell, home directory, lock status. Per-user and takes effect immediately.

Use Case (Cyber Defense context)

The tool for both directions of account hardening: granting a legitimate account the access it needs (adding to a group), and cutting off a compromised one immediately (locking it) without waiting to delete it outright.

Syntax
$ usermod [flags] <username>
Relevant Options
FlagWhat it does
-aG groupAdd the user to an additional group (without removing them from others)
-s shellChange the user's login shell
-L / -ULock / unlock the account
Examples
# Add a user to the sudo group
$ usermod -aG sudo user2

# Confirm what actually took effect
$ id user2

# Lock a compromised account immediately
$ usermod -L user2
Notes

Not the same as group policy — changes are per-user and immediate. Use id afterward to confirm exactly what took effect.

Caution

Modifying group membership or shell for the wrong account can lock a legitimate user out or hand an attacker more access — verify the target account before running.

See Also
id, adduser, passwd

▶kill— send a signal to a process, most often to stop it⚠ risk

A stateless firewall built around a Table → Chain → Rule structure, plus a default policy. Rules are checked top-down; the first match wins. Not always enabled by default — some distros use ufw as a friendlier front-end instead.

Use Case (Cyber Defense context)

Locking a box down to only the traffic it actually needs. Firewalls should follow the implicit deny principle: block by default, allow by exception. More open ports = larger attack surface.

The Filter Table's 3 Chains

OUTPUTTraffic leaving this host
FORWARDTraffic passing through this host to somewhere else
Core Syntax
FlagWhat it does
-PSet the default policy for a chain
-AAppend a new rule to a chain
-L --line-numbersList current rules with line numbers
-FFlush (delete) all rules
Examples
# List current rules
$ iptables -L --line-numbers

# Set default-deny policy on all 3 chains
$ iptables -P INPUT DROP
$ iptables -P OUTPUT DROP
$ iptables -P FORWARD DROP

# Allow incoming HTTP (port 80)
$ iptables -A INPUT -p tcp --dport 80 -j ACCEPT

# Allow outgoing responses to connections we started
$ iptables -A OUTPUT -p tcp -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT
Persisting Rules

Rules built with iptables -A/-P live in memory only and vanish on reboot unless explicitly saved. The save/restore mechanism varies by distro:

# Save current rules to a file
$ iptables-save > /etc/iptables/rules.v4

# Restore rules from that file (e.g. on boot, via a startup hook)
$ iptables-restore < /etc/iptables/rules.v4
Caution

iptables -F only use this with complete understanding — it can affect other services in unexpected ways. Document any flush for the team. Setting a default DROP policy before your allow rules are in place can lock out your own remote access — write the ACCEPT rules for established connections and your own management access first, then set the deny policy last.

One of the most common persistence mechanisms — a scheduled task that keeps re-establishing an attacker's access even after you've cleaned up the initial compromise. Always check both the per-user crontab and /etc/cron.d for anything unfamiliar.

▶ 03 Quick Start & Routine Checks 3 tracks
Three separate tracks: A is read-only recon — safe to run any time, on any box. B and C actively change the system, so they're kept separate from recon and from each other. Run A first. Only move into B or C once you understand what's already there.
▶ A Initial Recon & Routine Checks read-only
Look and understand before you touch anything. Nothing in this track changes the system.
  1. Confirm who you are and what you can do
    Check your own identity, group memberships, and who else has elevated access.
    $ id
$ cat /etc/sudoers
  2. Check the Holy Square of user management
    These four files are the foundation of who can log in and with what access.
    $ less /etc/passwd
$ less /etc/group
$ less /etc/shadow
$ less /etc/sudoers
  3. Enumerate accounts with real login shells
    Surface every account that can actually log in — an unexpected one is a strong compromise indicator.
    $ cat /etc/passwd | grep -E ':(/bin/(bash|sh))$' | awk -F ':' '{print $1}' > users
  4. Review running processes
    Look for anything unfamiliar, oddly named, or running from an unusual path.
    $ ps -ef --forest | less
  5. Check for persistence via cron
    Review both the per-user schedule and the system-wide cron directory.
    $ crontab -e
$ ls /etc/cron.d
  6. Glance at network config and listening ports
    Just looking here — confirm your own IP, then see what's listening and who's connected. Full network setup lives in Track C.
    $ ip a
$ ss -tulnp
$ nmap localhost
  7. Review the current firewall rule set
    See what's currently allowed. Building or changing rules lives in Track B — this step is only about seeing what's already there.
    $ iptables -L --line-numbers
$ ufw status verbose
  8. Spot-check for tampering
    A fast pass for common indicators before deciding what needs deeper investigation.
    $ find / -perm -4000 -type f 2>/dev/null
$ lsattr /etc/ssh/sshd_config
  9. Document everything
    Write down what you found before moving into Track B or C — this is your baseline.
▶ B Firewall Setup & Hardening active — changes the system
Order matters here. Writing the deny policy before your allow rules locks you out. See iptables and ufw/firewall-cmd for full flag references.
  1. Define what actually needs to be reachable
    List the management access you need (e.g. SSH) and the service ports this box legitimately serves, before writing a single rule.
  2. Write allow rules for that list first
    Every port that needs to stay open gets an explicit ACCEPT rule before anything gets blocked.
    # Example: allow SSH and HTTP
$ iptables -A INPUT -p tcp --dport 22 -j ACCEPT
$ iptables -A INPUT -p tcp --dport 80 -j ACCEPT
  3. Allow outbound responses to established connections
    Without this, replies to legitimate outbound traffic get dropped too.
    $ iptables -A OUTPUT -p tcp -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT
  4. Set the default-deny policy last
    Only after steps 2–3 are confirmed in place. This is the step that actually implements implicit deny.
    $ iptables -P INPUT DROP
$ iptables -P OUTPUT DROP
$ iptables -P FORWARD DROP
  5. Verify from a second session before closing your current one
    Open a new connection attempt (a second SSH session, a fresh terminal) to confirm you still have access — don't close the session you're working in until it's confirmed.
  6. Persist the rules so they survive a reboot
    Raw iptables rules are in-memory only by default and vanish on restart. Save them (method varies by distro — e.g. iptables-save, or use ufw/firewalld which persist automatically).
    $ iptables-save > /etc/iptables/rules.v4
  7. Document exactly what's open and why
    Every allowed port, tied to the service that needs it. Makes the next audit — and the next person — much faster.
▶ C Network Setup & Configuration active — changes the system
Which tool manages this varies by distro — see NetworkManager / systemd-networkd / netplan for that variation.
  1. Identify the interface and its current state
    Confirm which interface you're configuring and what it currently has assigned, if anything.
    $ ip a
  2. Assign the intended static IP
    Set the address and subnet mask for this host. Exact syntax depends on the distro's network manager — could be a GUI wired-connection dialog, a netplan YAML file, or nmcli.
    # Example using ip (temporary — won't survive reboot on its own)
$ ip addr add 192.168.1.12/24 dev eth0
  3. Set the default gateway
    Point the host at the router/gateway responsible for traffic leaving the local subnet.
    $ ip route add default via 192.168.1.1
  4. Verify DNS resolution
    Confirm the host can resolve names, not just reach IPs directly.
    $ cat /etc/resolv.conf
  5. Make the change persistent
    Manual ip commands don't survive a reboot. Confirm the change is saved through whichever network manager the distro actually uses.
  6. Confirm it actually applied
    Re-check the interface after applying — don't assume the config took effect just because no error was shown.
    $ ip a
  7. Test connectivity end-to-end
    Ping the gateway, then something beyond it, then confirm DNS-based resolution works too.
    $ ping -c 3 192.168.1.1
  8. Document the IP scheme
    Record what's assigned where — critical for the team when multiple boxes are being configured together.
▶ 04 Reference / Glossary concepts & context
Terminal
The program/window that gives you a text-based way to interact with the computer — it displays text and passes along whatever you type. On its own, a terminal doesn't understand commands; it's just the window. What actually interprets what you type is the shell running inside it.
Shell
The program that reads what you type into the terminal, interprets it as commands, and runs them — bash is the most common on Linux, though zsh and others exist too. "Shell" and "terminal" get used interchangeably in casual conversation, but they're different layers: the terminal is the window, the shell is the interpreter running inside it. Bash scripting, environment variables, and command syntax are all shell concepts, not terminal ones.
Absolute vs. Relative Path
An absolute path always starts from the filesystem root (/) — e.g. /home/user/Desktop/. A relative path starts from wherever you currently are (pwd) — e.g. var/www/html/. . means the current directory, .. means the parent directory, and ~ means your home directory.
root vs. /root vs. /
root user (UID 0) is the system administrator account. /root is that user's home directory. / is the root of the entire filesystem — the top-level directory everything else lives under. Three different things that share a name.
UID / GID Ranges
User ID 0 is always root. IDs below 1000 are typically reserved for system services. Real human user accounts usually start at UID 1000 and above.
Octal File Permissions
Each permission digit is a sum: read = 4, write = 2, execute = 1. rwx = 4+2+1 = 7. So rwxr--r-- = 744, and r-x-w---x = 755. Three digits total, for owner / group / others.
PAM (Pluggable Authentication Module)
The system-wide framework that governs authentication — login, sudo, SSH, and more all defer to it. Config location differs by distro family (common-auth on Debian, system-auth/password-auth on RHEL).
iptables Chains & Implicit Deny
The 3 core chains are INPUT (incoming), OUTPUT (outgoing), and FORWARD (pass-through) traffic. A firewall following implicit deny blocks everything by default and only allows specific, intentional exceptions — the opposite of blocking a known-bad list.
STDIN / STDOUT / Pipes
STDIN (<) feeds input into a command. STDOUT (>) redirects a command's output into a file. A pipe (|) connects one command's output directly to the next command's input — the building block of most chained one-liners.
Environment Variables
Variables like $PATH that shape how the shell behaves — in this case, which directories it searches (and in what order) when resolving a command name. View them all with env.
Distro Families
Distros cluster into families that share tooling: Debian-based (Debian, Ubuntu — apt), RHEL-based (RHEL, CentOS, Fedora — yum), plus others like Alpine (apk) and Arch (pacman). Knowing the family tells you which command syntax to expect.
Least Privilege
Give every account and process only the access it actually needs to do its job — nothing more. Reduces how much damage any single compromised account or service can do.
The sudo Group
One of the highest-value things to check on any system — who's in it defines who can act as root. An unexpected member is one of the fastest indicators of compromise to check for.
SUID / SGID
Special permission bits that let a file run with the permissions of its owner (SUID) or group (SGID) rather than the user who executed it. Legitimate uses exist (e.g. passwd needs to write to a root-owned file), but an unexpected SUID root binary is one of the most common privilege-escalation footholds — find them with find -perm -4000.
ACL (Access Control List)
A finer-grained permission layer on top of the standard owner/group/others model, letting you grant access to a specific extra user or group. Managed with getfacl/setfacl; shown as a trailing + in ls -l output.
IOC (Indicator of Compromise)
A specific, observable artifact that suggests a system has been compromised — a file hash, an IP address, a filename, a registry-style value, a suspicious process name. Investigations are largely the process of collecting and matching IOCs.
Persistence
Any mechanism an attacker sets up to survive a reboot or maintain access after the initial compromise is cleaned up — a cron job, a modified startup service, an added SSH key, an extra user account. Checking known persistence points (cron, services, authorized_keys, sudoers) is a core part of incident response.
Attack Surface
Everything on a system that's reachable and could potentially be exploited — every open port, running service, and installed package adds to it. Hardening is largely the process of shrinking this: disabling what isn't needed.
Anti-Forensics
Techniques used to hide evidence of an intrusion — clearing shell history, touching timestamps to disguise when a file was really modified, deleting or tampering with logs. Their presence (e.g. a suspiciously empty history file) can itself be a signal something happened.
/var/log vs. the systemd Journal
Two overlapping logging systems exist on most modern distros: traditional plaintext files under /var/log, and the binary systemd journal read with journalctl. Depending on the distro's configuration, one, the other, or both may hold the events you're looking for — check both if something seems to be missing.
CIDR Notation & Subnet Mask
Two ways of expressing the same thing: how many bits of an IP address identify the network vs. the individual host. 192.168.1.12/24 means the first 24 bits are the network portion — equivalent to a subnet mask of 255.255.255.0. A smaller number after the slash (e.g. /16) means a larger network with more possible hosts.
Default Gateway
The router a host sends traffic to when the destination isn't on its local subnet — effectively "the way out." Set with ip route add default via. Get this wrong and the host can talk to local devices but nothing beyond them.
DNS & /etc/resolv.conf
DNS resolves human-readable names (like a hostname) to IP addresses. On Linux, which DNS server(s) a host queries is typically listed in /etc/resolv.conf — worth checking directly if name resolution isn't working even though raw IP connectivity is fine.
Connection Tracking & Stateful Firewalls
A stateful firewall remembers which connections it already allowed, so it can automatically permit the return traffic without a separate rule for it. This is what --ctstate ESTABLISHED,RELATED refers to in iptables rules — "let responses to traffic we already approved back in."
SYN Cookies
A kernel-level defense against SYN-flood denial-of-service attacks, where an attacker opens huge numbers of half-finished connections to exhaust a server's resources. Enabling SYN cookies (sysctl) lets the kernel handle those connection attempts without committing resources until they're confirmed legitimate.
