▶ 01 Linux Commands by category
File & Directory Operations
▶ls— list files and directories
Definition

Lists the contents of a directory. With no argument, lists the current working directory.

Use Case (Cyber Defense context)

First command run in almost any directory to see what's there — including hidden files that might be a dropped payload or persistence mechanism.

Syntax
$ ls [flags] [filepath]
Relevant Options
FlagWhat it does
-lLong/detailed view — permissions, owner, size, date
-aShow all files, including hidden dotfiles
-tSort by modification time, newest first
-SSort by file size, largest first
-iShow inode numbers
-RRecursive listing through subdirectories
Examples
# Detailed listing including hidden files
$ ls -la user1/Downloads

# What changed most recently in this directory?
$ ls -lat

# Find unusually large files
$ ls -laS
▶cd— change directory
Definition

Changes the shell's current working directory. Accepts absolute paths (start with /), relative paths, ./.., or ~ for the home directory.

Syntax
$ cd [path]
Examples
# Absolute path
$ cd /home/user1/Desktop/

# Previous directory
$ cd ..

# Home directory shortcut
$ cd ~/Downloads
Notes

. = current directory, .. = parent directory, ~ = home directory. Root user's home is /root, not to be confused with / (filesystem root).

▶pwd— print working directory
Definition

Prints the full absolute path of the directory you're currently in — the reference point for any relative path you type next.

Syntax
$ pwd
▶touch— create an empty file / update timestamp
Definition

Creates a new empty file if it doesn't exist, or updates the modified timestamp if it does.

Syntax
$ touch [flags] [filename/filepath]
Notes

An attacker touching files to fake or hide modification times is worth watching for during investigations — compare timestamps against expected change windows.

▶mkdir— make a new directory
Definition

Creates a new directory at the given path.

Syntax
$ mkdir [flags] [path/directory_name]
Relevant Options
FlagWhat it does
-p / --parentCreate any missing parent directories along the path
▶cp— copy files or directories
Definition

Copies a file or directory from a source path to a destination path.

Syntax
$ cp [source] [destination]
▶mv— move or rename a file
Definition

Moves a file or directory to a new location. Also used to rename, since renaming is just moving to a new name in the same directory.

Syntax
$ mv [source] [destination]
▶rm— remove files or directories⚠ risk
Definition

Deletes files or directories. There is no trash can — deletion is immediate and permanent.

Syntax
$ rm [flags] [filepath/filename]
Relevant Options
FlagWhat it does
-f / --forceDon't prompt, just remove
-r / --recursiveRemove a directory and everything inside it
Caution

Irreversible. rm -rf on the wrong path can wipe far more than intended — double-check the path before hitting enter, especially with wildcards.

▶cat— concatenate / print file contents
Definition

Prints file contents to the terminal, or concatenates multiple files together.

Use Case (Cyber Defense context)

Quick way to dump a config or log file to read directly, or to feed into a pipe for filtering with grep/awk.

Syntax
$ cat [filename]
See Also
grep, head / tail, less / more
File Forensics & Integrity
▶find— locate files by name, permission, owner, or age
Definition

Searches a directory tree for files matching criteria — name, permission bits, owner, modification time, and more. Far more powerful than ls for hunting across a whole filesystem.

Use Case (Cyber Defense context)

One of the highest-value hunting commands available: surface SUID/SGID binaries (a privilege-escalation favorite), orphaned files, world-writable files, or anything modified recently — all classic signs of tampering.

Syntax
$ find <path> [criteria]
Relevant Options
FlagWhat it does
-perm -4000Find files with the SUID bit set
-perm -2000Find files with the SGID bit set
-nouser / -nogroupFind files owned by a UID/GID that no longer exists
-mtime -nModified within the last n days
-newer fileModified more recently than a reference file
-perm -o+wFind world-writable files
-type f / -type dRestrict to files or directories
Examples
# Find every SUID binary on the system
$ find / -perm -4000 -type f 2>/dev/null

# Files modified in the last 24 hours
$ find / -mtime -1 -type f 2>/dev/null

# Orphaned files (owner no longer exists — often a leftover from a removed account)
$ find / -nouser -o -nogroup 2>/dev/null

# World-writable files — anyone can modify these
$ find / -perm -o+w -type f 2>/dev/null
See Also
stat, chmod
▶stat— detailed file metadata and timestamps
Definition

Shows detailed metadata for a file: exact permissions, owner, inode, and all three timestamps — access, modify, and change (metadata change) time. More precise than ls -l for building a timeline.

Use Case (Cyber Defense context)

When timing matters — was this config edited before or after the service restarted? stat gives the exact timestamps needed to build that timeline.

Syntax
$ stat <file>
▶file— identify true file type
Definition

Inspects a file's actual contents (not its extension) to identify what type it really is.

Use Case (Cyber Defense context)

Catches disguised files — an executable renamed with a .jpg or .txt extension still shows up as what it really is (e.g. an ELF binary or shell script).

Syntax
$ file <filename>
▶diff— compare two files line by line
Definition

Shows the line-by-line differences between two files.

Use Case (Cyber Defense context)

Compare a live config against a known-good backup to spot exactly what an attacker (or a misconfiguration) changed.

Syntax
$ diff <file1> <file2>
▶sha256sum / md5sum— generate and verify file hashes
Definition

Computes a cryptographic hash of a file's contents. Identical files produce identical hashes; any change to the file, even one byte, produces a completely different hash.

Use Case (Cyber Defense context)

Verify a binary or config hasn't been tampered with by comparing its hash against a known-good value, or confirm a downloaded package matches its published checksum before trusting it.

Syntax
$ sha256sum <file>
$ md5sum <file>
Notes

Prefer sha256sum over md5sum when possible — MD5 is cryptographically broken and shouldn't be relied on for anything security-critical.

▶du / df— disk usage by file/directory vs. by filesystem
Definition

du shows how much space specific files/directories are using. df shows overall free/used space per mounted filesystem.

Use Case (Cyber Defense context)

A disk quietly filling up can mean staged exfiltration data, an oversized log from an attack in progress, or a crypto-miner writing junk to disk.

Syntax
$ du -sh <path>   # human-readable total for a path
$ df -h            # human-readable free space per filesystem

Text Processing & Search
▶grep— search text using patterns
Definition

grep (Global Regular Expression Print) scans input line-by-line and prints any line that matches a given pattern or string. Reads from a file argument, multiple files, or STDIN — commonly used at the end of a pipe chain.

Use Case (Cyber Defense context)

Primary tool for hunting during initial triage: pulling suspicious lines out of logs, finding accounts with shell access in /etc/passwd, searching config files for a setting, or filtering the output of another command down to what matters. Combine with awk/sed for full log-hunting pipelines.

Syntax
$ grep [options] "pattern" <file>
# or, from a pipe:
$ cat <file> | grep "pattern"
Relevant Options
FlagWhat it does
-iCase-insensitive match
-r / -RRecursive search through a directory
-vInvert match — show lines that don't match
-EExtended regex (enables |, +, {} without escaping)
-nShow line numbers with matches
-cCount matching lines instead of printing them
-lPrint only filenames that contain a match
--colorHighlight matched text in output
-wMatch whole words only
-A n / -B n / -C nShow n lines of context after / before / around a match
-oPrint only the matched portion of the line, not the whole line
-f fileRead patterns to search for from a file — good for matching a list of known-bad IPs or strings
Examples
# Find all users with a bash or sh shell in /etc/passwd
$ cat /etc/passwd | grep -E ':(/bin/(bash|sh))$'

# Search recursively for a string across config files
$ grep -r "PermitRootLogin" /etc/ssh/

# Case-insensitive search with line numbers
$ grep -in "error" /var/log/auth.log

# Read a failed-login hit with 3 lines of context on each side
$ grep -A3 -B3 "Failed password" /var/log/auth.log

# Match a list of known-bad indicators against a log
$ grep -f iocs.txt /var/log/syslog

# Chained: list usernames that have a real login shell
$ cat /etc/passwd | grep -E ':(/bin/(bash|sh))$' | awk -F ':' '{print $1}' > users
See Also
sed, awk, redirection & pipes
▶sed— stream editor for find/replace in files⚠ risk
Definition

Applies a scripted transformation (most commonly find-and-replace) to text as it streams through, line by line. Supports regex pattern matching.

Use Case (Cyber Defense context)

Scripting out bulk config changes — e.g. rewriting a setting across a file, or across many files, without opening an editor.

Syntax
$ sed <script> <filename>
Relevant Options
Flag/PartWhat it does
-iEdit the file in place (overwrites it)
gGlobal — replace all matches on a line, not just the first
Examples
# Replace all occurrences of "pattern" with "replace" in a file, in place
$ sed -i 's/pattern/replace/g' file.txt
Caution

-i overwrites the original file with no confirmation and no backup by default. Test the pattern without -i first if unsure.

▶awk— field-based text filtering and scripting
Definition

Processes text a line at a time and splits each line into fields (like columns), so you can select, filter, or transform specific fields. Effectively runs a small program over each line of input.

Use Case (Cyber Defense context)

Extracting one column out of structured output — usernames from /etc/passwd, a specific field from a CSV log, or a PID from ps output.

Syntax
$ awk <options> <script> <input>
Examples
# Print the 2nd comma-separated field of a CSV
$ awk -F ',' '{print $2}' data.csv
▶< > |— I/O redirection & pipes
Definition

STDIN (<) feeds a string/file in as input. STDOUT (>) redirects a command's output to a file (overwriting it). A pipe (|) sends the output of one command directly into the input of the next, chaining tools together.

Use Case (Cyber Defense context)

This is how most real investigation one-liners are built: cat a file, pipe it through grep to filter, pipe that through awk to extract a field, then redirect the result into a file for later reference.

Examples
# Break a long chained command down at each pipe and reason through
# one segment at a time:
$ cat /etc/passwd | grep -E ':(/bin/(bash|sh))$' | awk -F ':' '{print $1}' > users
See Also
grep, awk
Permissions & Ownership
▶chmod— change file permissions⚠ risk
Definition

Changes read/write/execute permissions on a file or directory, either symbolically (rwx) or numerically (octal, e.g. 744). See the Reference section for how octal maps to rwx.

Syntax
$ chmod <mode> <file>
Relevant Options
FlagWhat it does
-RApply recursively to a directory and everything inside it
--reference=fileCopy the mode from another file instead of typing octal
Examples
# rwxr--r-- 
$ chmod 744 script.sh

# r-x-w---x
$ chmod 755 script.sh
Caution

Overly permissive modes (777) can open up a system unintentionally — set only what's needed. -R is especially dangerous: it applies to every file underneath, including ones that needed a different, more restrictive mode. Spot-check a directory tree before running it recursively.

See Also
chown, chattr
▶chown— change file owner/group
Definition

Changes which user and/or group owns a file.

Syntax
$ chown user:group <file>
Examples
$ chown user1:group1 notes.txt
$ chown root:root notes.txt
See Also
chmod
▶chattr— set/unset the immutable attribute⚠ risk
Definition

Changes low-level filesystem attributes on a file. The most relevant one for defense is the immutable bit (i) — while set, the file can't be modified, deleted, or renamed by anyone, including root, until it's unset.

Use Case (Cyber Defense context)

Lock down a critical config file so it can't be silently overwritten by an attacker (or a script) — even with root access, the immutable bit has to be removed first.

Syntax
$ chattr +i <file>   # make immutable
$ chattr -i <file>   # remove immutable bit
Caution

If you set +i and forget, future legitimate edits (including automated ones) will silently fail. Check with lsattr before troubleshooting a file that "won't save."

See Also
lsattr
▶lsattr— list file attributes
Definition

Displays the filesystem attributes on a file, including whether the immutable bit is set.

Syntax
$ lsattr <file>
See Also
chattr
User & Access Management
▶sudo / su— run as another user or root⚠ risk
Definition

sudo <command> runs a single command as root (or another user). su <user> switches to that user's shell entirely. su - switches and also loads that user's environment.

Syntax
$ sudo <command>
$ sudo -i        # root login shell
$ sudo su        # root shell via sudo
$ su <user>
$ su -
Caution

Who's in the sudo group is one of the first things worth checking on any box — an unexpected member is a red flag. Check /etc/sudoers for rules that shouldn't exist.

▶adduser / useradd— create a new user
Definition

adduser is a friendlier wrapper: it prompts for a password and creates a home directory automatically. useradd is the lower-level, less convenient tool — it doesn't create a home directory or set a password unless told to.

Notes

An unfamiliar account showing up from either of these is worth investigating immediately — check its UID, shell, and home directory.

▶usermod / id— modify a user / show identity & groups⚠ risk
Definition

usermod changes an existing user's settings (groups, shell, home directory, lock status). id prints a user's UID, GID, and group memberships — useful for confirming exactly what access an account has.

Notes

usermod is not the same as group policy — it's per-user, immediate. UID 0 is always root/admin; services typically run below UID 1000, real user accounts above it.

Caution

Modifying group membership or shell for the wrong account can lock a legitimate user out or hand an attacker more access — verify the target account before running.

▶passwd / chpasswd— set or change a password⚠ risk
Definition

passwd changes a password interactively (for the current user, or for another user when run with privileges). chpasswd reads username:password pairs and sets them in bulk — built for automation/scripting.

Syntax
$ passwd            # change your own password
$ passwd user2      # change user2's password
$ echo "user2:newpassword" | chpasswd
Notes

chpasswd input can also be typed manually and terminated with Ctrl + D instead of piping from echo.

Caution

Resetting the wrong account's password locks that user out immediately — confirm the username first, and make sure you have another way in before changing your own.

▶visudo— safely edit /etc/sudoers
Definition

Opens /etc/sudoers in an editor with syntax checking on save — if the edit would break the file, it warns you instead of writing broken syntax.

Use Case (Cyber Defense context)

The correct way to change sudo rules. Editing /etc/sudoers directly with nano/vim and introducing a syntax error can lock every account out of sudo at once.

Syntax
$ visudo
▶getfacl / setfacl— view and set fine-grained Access Control Lists
Definition

Extends permissions beyond the basic owner/group/others model — lets you grant a specific user or group access to a file without changing its base permissions.

Use Case (Cyber Defense context)

When a hardening task needs more precision than chmod/chown can express — e.g. one extra user needs read access without changing group ownership. Also worth checking during an audit: ACLs are easy to miss since ls -l doesn't show them fully.

Syntax
$ getfacl <file>
$ setfacl -m u:<user>:rw <file>
Notes

A file with ACLs set shows a + at the end of its permission string in ls -l — easy to miss if you're not looking for it.

Process Management
▶ps— list running processes
Definition

Lists processes. On its own, only shows processes tied to the current terminal — use ps aux to see every process on the system.

Use Case (Cyber Defense context)

Core hardening/hunting command — scan running processes for anything unexpected, unusually named, or running from a strange path.

Relevant Options
FlagWhat it does
auxEvery process, every user, BSD-style output
-efEvery process, full-format listing (includes PPID)
--forestDraws the parent/child process tree visually
-o pid,ppid,user,cmdShow only the fields you specify
Examples
# All processes, all users
$ ps aux

# Visual process tree — spot a suspicious parent/child chain,
# e.g. a webserver spawning a shell
$ ps -ef --forest

# Just the fields you care about
$ ps -eo pid,ppid,user,cmd
See Also
kill, pgrep, lsof
▶kill— terminate a process by ID⚠ risk
Definition

Sends a signal to a process, most commonly to terminate it. kill -9 sends SIGKILL — an immediate, forceful kill that the process can't intercept or clean up after.

Syntax
$ kill -9 <PID>
Caution

SIGKILL gives the process no chance to shut down gracefully — it can leave lock files, corrupt in-progress writes, or drop open connections uncleanly. Use it when the process needs to die immediately, not as a default first move.

See Also
ps, pgrep
▶pgrep— find a process ID by name
Definition

Searches running processes by name and returns matching PIDs — faster than piping ps aux through grep for the same result.

Syntax
$ pgrep <process_name>
▶lsof— list open files and the processes holding them
Definition

Lists open files — and on Linux, network sockets count as files too — along with the process holding each one open. The connective tissue between "what's listening on this port" and "which exact process that is."

Use Case (Cyber Defense context)

Pair with netstat/ss when you find a suspicious open port — lsof tells you exactly which process and PID owns it. Also useful for finding which process is holding a file open (e.g. one you're trying to delete or that's writing to disk unexpectedly).

Syntax
$ lsof [options]
Relevant Options
FlagWhat it does
-i :portShow what's using a specific port
-p PIDShow everything a specific process has open
-u userShow everything a specific user has open
Examples
# What process is listening on port 4444?
$ lsof -i :4444

# Every file/socket a suspicious PID has open
$ lsof -p 1337
See Also
netstat / ss, ps
Logs & Login History
▶journalctl— view systemd logs
Definition

Reads the systemd journal — the binary log store used by most modern distros alongside or instead of traditional plaintext files in /var/log.

Use Case (Cyber Defense context)

Central place to review boot logs, service failures, and authentication events on systemd-based systems — often faster than hunting through individual log files.

Relevant Options
FlagWhat it does
-u serviceShow logs for one specific service
-fFollow — stream new log entries live
--since "time"Only show entries after a given time
-bOnly show logs from the current boot
Examples
# Live-tail SSH auth activity
$ journalctl -u sshd -f

# Everything logged in the last hour
$ journalctl --since "1 hour ago"
▶history— view shell command history⚠ risk
Definition

Shows previously run commands for the current shell session, backed by a history file (commonly ~/.bash_history).

Use Case (Cyber Defense context)

Reviewing a compromised or suspicious account's history can reveal exactly what an attacker ran. Just as important defensively: know that clearing history (history -c, unsetting HISTFILE) is a common anti-forensic move — an empty or missing history file on an active account is itself a red flag.

Syntax
$ history
Caution

Don't clear history on a box you're investigating — it's evidence. Only clear your own working history, and only when that's genuinely appropriate.

▶who / w / last / lastlog— see who's logged in and login history
Definition

who/w show who's currently logged in (and what they're doing). last shows a history of logins/logouts. lastlog shows the most recent login for every account, including ones that have never logged in.

Use Case (Cyber Defense context)

Fast way to spot an account logging in from an unexpected location, at an unexpected time, or an account that suddenly has activity after sitting dormant.

Syntax
$ who
$ w
$ last
$ lastlog
Service Management
▶systemctl— start, stop & manage background services (with distro/init-system variants)⚠ risk
Definition

Controls services — programs that run in the background and are managed by the system's init process (things like sshd, nginx, cron). The command you use depends on which init system the distro runs, not the distro name itself.

Use Case (Cyber Defense context)

Check what's running, disable services you don't need (shrinks attack surface), restart a service after fixing its config, or stop something suspicious that keeps re-launching. Usually one of the first things to audit on a new box.

Distro / Init System Variations

Same action, different command depending on what the target system uses:

System typeCommand
systemd (most modern distros — Ubuntu, Debian 8+, RHEL/CentOS 7+, Fedora)systemctl start sshd
Older SysV-init distros (no systemd)/etc/init.d/sshd start
Generic wrapper (works on many systems as a fallback if unsure)service sshd start
Syntax
$ systemctl <action> <service>
$ service <service> <action>
Relevant Actions
ActionWhat it does
statusShow whether a service is running
start / stopStart or stop the service now
restartStop then start (e.g. after a config change)
enable / disableToggle whether it launches automatically at boot
maskBlock a service from being started at all, even manually — stronger than disable
Examples
# Check if SSH is running (systemd)
$ systemctl status sshd

# Same check on a system without systemctl
$ service sshd status

# Fully disable a service so it can't be restarted
$ systemctl mask <service>

# Legacy init.d fallback (rare — mostly older/minimal distros)
$ /etc/init.d/sshd status
Caution

Stopping or masking the wrong service (e.g. your own SSH access) can lock you out of the box remotely. Confirm the service name and your access path before disabling anything remote-facing.

Package Management
▶apt / yum / apk / pacman— install, update & remove software (distro variants)
Definition

Every distro family ships its own package manager for installing, updating, and removing software. The action is the same across all of them; only the command name and exact flags change.

Distro Variations
Distro familyPackage manager
Debian-based (Debian, Ubuntu)apt
RHEL-based (RHEL, CentOS, Fedora)yum
Alpineapk
Archpacman
Examples
# Debian-based
$ apt update
$ apt upgrade
$ apt install <package>
$ apt purge <package>

# RHEL-based
$ yum update
$ yum upgrade
$ yum install <package>
$ yum remove <package>
Notes

Knowing the package manager tells you the distro family at a glance — useful shorthand when jumping onto an unfamiliar box mid-competition or mid-incident.

Scheduling
▶crontab— view/edit a user's scheduled tasks⚠ risk
Definition

Edits the current user's cron table — a list of commands set to run automatically at defined intervals (every day/week/month, etc).

Use Case (Cyber Defense context)

Cron is a classic persistence mechanism — always check for scripts that shouldn't be there. See the full write-up under Programs & Tools for the broader cron system, including /etc/cron.d.

Syntax
$ crontab -e
Caution

Editing or removing a cron entry you don't recognize without documenting it first can destroy evidence of how a system was compromised.

Networking
▶ip— show and configure network interfaces & routes
Definition

The modern tool for both viewing and configuring networking — interfaces, addresses, and routes. ifconfig (Linux) / ipconfig (Windows) are older/alternate equivalents for the viewing side only.

Use Case (Cyber Defense context)

Beyond just viewing — ip addr assigns an address to an interface, and ip route manages where traffic goes, including the default gateway. Both are usually temporary until made persistent through the distro's network manager.

Syntax
$ ip a                                    # view interfaces & addresses
$ ip addr add <ip>/<mask> dev <iface>      # assign an address
$ ip addr del <ip>/<mask> dev <iface>      # remove an address
$ ip route show                           # view the routing table
$ ip route add default via <gateway>      # set default gateway
$ ifconfig                                 # older equivalent for viewing
Examples
# Assign a static IP to eth0
$ ip addr add 192.168.1.12/24 dev eth0

# Point this host at its gateway
$ ip route add default via 192.168.1.1
Notes

Changes made this way are temporary — they don't survive a reboot on their own. See NetworkManager / systemd-networkd / netplan for making them persistent, and the CIDR/Subnet Mask and Default Gateway glossary entries if the /24 notation is unfamiliar.

▶ping— test basic reachability to a host
Definition

Sends ICMP echo requests to a target and reports whether — and how quickly — it responds. The simplest possible connectivity test.

Use Case (Cyber Defense context)

First check after any network change: can this host reach its gateway? Can it reach something beyond the gateway? A failure at the gateway step points to local config; a failure only beyond it points to routing or the far side.

Syntax
$ ping [options] <host>
Relevant Options
FlagWhat it does
-c nSend exactly n packets, then stop (default runs forever)
Examples
# Confirm the gateway is reachable, 3 packets and stop
$ ping -c 3 192.168.1.1
Notes

Some hosts (Windows especially) block ICMP by default, so a failed ping doesn't always mean the host is down or unreachable — it may just be filtered.

▶netstat / ss— view network connections & listening ports
Definition

Shows active network connections, listening ports, and the processes behind them. netstat may require installing net-tools on newer distros; ss is the modern built-in replacement.

Use Case (Cyber Defense context)

Confirm exactly what's listening on the box and where connections are going — a fast way to spot an unexpected open port or an outbound connection to somewhere it shouldn't be. Pair with lsof to identify exactly which process owns a given port.

Relevant Options
FlagWhat it does
-tTCP connections
-uUDP connections
-lListening sockets only
-nNumeric — skip DNS resolution (faster, and won't tip off a listener)
-pShow the owning process/PID
Examples
# Everything listening, with the process that owns it
$ netstat -tulnp
$ ss -tulnp
See Also
lsof
▶tcpdump— capture and inspect live network traffic
Definition

Captures packets directly off a network interface and prints or saves them for inspection. Goes a level deeper than netstat/ss — instead of just showing what's connected, it shows the actual traffic.

Use Case (Cyber Defense context)

Confirm what's actually being sent over a suspicious connection, verify a service is really talking the protocol it claims to, or capture evidence of an ongoing attack for later analysis.

Syntax
$ tcpdump [options]
Relevant Options
FlagWhat it does
-i interfaceCapture on a specific interface (e.g. eth0)
-nDon't resolve hostnames — faster, cleaner output
-w fileWrite the capture to a file for later analysis
port NFilter to a specific port
Examples
# Watch traffic on port 4444 in real time
$ tcpdump -i eth0 -n port 4444

# Save a capture to review later
$ tcpdump -i eth0 -w capture.pcap
▶nmap— scan for open ports on the network
Definition

Quickly identifies open ports on a host or across the network, which can help surface unexpected services and infer firewall configuration.

Use Case (Cyber Defense context)

Run against your own boxes to verify only intended ports are exposed — treat any unexpected open port as something to investigate immediately.

Firewall
The full iptables rule engine is covered under Programs & Tools. The two commands below are simpler front-ends for it, and vary by distro.
▶ufw / firewall-cmd— simplified firewall front-ends (distro variants)
Definition

Friendlier commands that sit on top of the underlying kernel firewall so you don't have to write raw iptables rules by hand. ufw (Uncomplicated Firewall) is Debian/Ubuntu's default. firewalld, controlled via firewall-cmd, is RHEL/CentOS/Fedora's default.

Distro Variations
Distro familyCommand
Debian-based (Debian, Ubuntu)ufw
RHEL-based (RHEL, CentOS, Fedora)firewall-cmd (firewalld)
Examples
# ufw — enable, allow SSH, check status
$ ufw enable
$ ufw allow 22/tcp
$ ufw status verbose

# firewalld — allow a port, then make it persistent
$ firewall-cmd --add-port=80/tcp
$ firewall-cmd --add-port=80/tcp --permanent
$ firewall-cmd --list-all
Notes

Either one may not be installed/enabled by default — the raw iptables rules are always underneath, so it's worth checking both layers when auditing a firewall.

Kernel & Hardening
▶sysctl— view and tune kernel parameters⚠ risk
Definition

Reads and sets kernel runtime parameters — network stack behavior, memory handling, and other low-level settings that live under /proc/sys. Changes can be made live or made permanent via /etc/sysctl.conf.

Use Case (Cyber Defense context)

Direct system hardening: disable IP forwarding on a host that shouldn't route traffic, enable SYN cookies to resist SYN-flood attacks, disable ICMP redirects, restrict core dumps.

Syntax
$ sysctl <parameter>              # read current value
$ sysctl -w <parameter>=<value>   # set live (not persistent)
Examples
# Disable IP forwarding (this box shouldn't route traffic)
$ sysctl -w net.ipv4.ip_forward=0

# Enable SYN cookies to resist SYN-flood DoS
$ sysctl -w net.ipv4.tcp_syncookies=1
Caution

Live changes with -w don't survive a reboot — and some kernel parameters can break networking or services if set incorrectly. Test before writing changes into /etc/sysctl.conf permanently.

man <command> opens the full manual page for a command. --help as a flag on most commands prints a short usage summary. less/more page through long output or files one screen at a time — essential on headless servers where you can't just scroll a GUI window.

head prints the first lines of a file; tail prints the last lines. Fast way to check a huge log file without opening the whole thing.

Environment & Shell
▶$PATH / env— command search order & environment variables
Definition

$PATH is the environment variable that defines which directories the shell searches, and in what order, when you type a command name. env lists every currently set environment variable.

Use Case (Cyber Defense context)

An attacker can plant a malicious binary earlier in $PATH than the real one, so a common command silently runs their version instead. Worth checking $PATH order if something behaves unexpectedly.

Syntax
$ echo $PATH
$ env
▶alias— create a shortcut for a longer command
Definition

Defines a shorthand name that expands to a longer command when typed.

Notes

Worth checking a shell's aliases when investigating a box — an alias can quietly redirect a trusted command name to something malicious.

▶bash scripts— running and writing shell scripts
Definition

A bash script is a file of shell commands run in sequence. It can be executed two ways, and bash syntax (like for-loops) can also be run directly on the command line without a script file at all.

Syntax
$ ./my_script.sh
$ bash my_script.sh

# inline for-loop, no script file needed
$ for line in $(cat poem); do echo $line; done
Notes

./file_name requires the file to have the executable (x) permission bit set — see chmod. bash file_name works without it.

▶ 02 Programs & Tools multi-command systems
▶iptables— host-based firewall rule engine⚠ risk
Definition

A stateless firewall built around a Table → Chain → Rule structure, plus a default policy. Rules are checked top-down; the first match wins. Not always enabled by default — some distros use ufw as a friendlier front-end instead.

Use Case (Cyber Defense context)

Locking a box down to only the traffic it actually needs. Firewalls should follow the implicit deny principle: block by default, allow by exception. More open ports = larger attack surface.

The Filter Table's 3 Chains
ChainApplies to
INPUTTraffic coming into this host
OUTPUTTraffic leaving this host
FORWARDTraffic passing through this host to somewhere else
Core Syntax
FlagWhat it does
-PSet the default policy for a chain
-AAppend a new rule to a chain
-L --line-numbersList current rules with line numbers
-FFlush (delete) all rules
Examples
# List current rules
$ iptables -L --line-numbers

# Set default-deny policy on all 3 chains
$ iptables -P INPUT DROP
$ iptables -P OUTPUT DROP
$ iptables -P FORWARD DROP

# Allow incoming HTTP (port 80)
$ iptables -A INPUT -p tcp --dport 80 -j ACCEPT

# Allow outgoing responses to connections we started
$ iptables -A OUTPUT -p tcp -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT
Persisting Rules

Rules built with iptables -A/-P live in memory only and vanish on reboot unless explicitly saved. The save/restore mechanism varies by distro:

# Save current rules to a file
$ iptables-save > /etc/iptables/rules.v4

# Restore rules from that file (e.g. on boot, via a startup hook)
$ iptables-restore < /etc/iptables/rules.v4
Caution

iptables -F only use this with complete understanding — it can affect other services in unexpected ways. Document any flush for the team. Setting a default DROP policy before your allow rules are in place can lock out your own remote access — write the ACCEPT rules for established connections and your own management access first, then set the deny policy last.

Keep a long-running task (a scan, a log tail, a monitoring loop) alive in a detached session while you work elsewhere, then reattach later without losing anything.

The framework that manages authentication across the system — how login, sudo, and other services decide whether to let a user in. Configured through a stack of modules rather than one file.

Core system hardening target — reviewing the PAM config can reveal weakened or bypassed authentication rules planted by an attacker.

▶Cron— scheduled task system⚠ risk
Definition

Cron runs tasks automatically at regular intervals — daily, weekly, monthly, or on a custom schedule. Per-user schedules are edited with crontab -e; system-wide entries live in /etc/cron.d.

Use Case (Cyber Defense context)

One of the most common persistence mechanisms — a scheduled task that keeps re-establishing an attacker's access even after you've cleaned up the initial compromise. Always check both the per-user crontab and /etc/cron.d for anything unfamiliar.

Examples
# Edit current user's scheduled tasks
$ crontab -e

# Check system-wide cron entries
$ ls /etc/cron.d
Notes

If a scheduled task has no legitimate use, disable it — systemctl stop/disable/mask the cron service is a last resort if the whole subsystem is compromised, but usually removing the specific malicious entry is the right move.

▶NetworkManager— network connection management service
Definition

Manages network connections and interfaces at the OS level. Which service handles this depends on the distro — NetworkManager, systemd-networkd, and netplan are the common ones.

Use Case (Cyber Defense context)

Make sure the relevant service is actually running (check with systemctl) before troubleshooting connectivity — and always verify network changes actually applied and persisted.

▶auditd— kernel-level audit logging
Definition

The Linux Audit daemon logs security-relevant events at the kernel level — file access, syscalls, authentication events — far more granular than standard syslog. Rules are managed with auditctl, and logs are searched with ausearch.

Use Case (Cyber Defense context)

The real answer to "who touched this file, and when." Set a watch rule on a critical file (like /etc/passwd or /etc/sudoers) and get a log entry for every read, write, or attribute change against it — including by root.

Examples
# Watch a critical file for any write/attribute change
$ auditctl -w /etc/passwd -p wa -k passwd_watch

# Search the audit log for events tagged with that watch
$ ausearch -k passwd_watch
Notes

Not installed/running by default on every distro — check with systemctl status auditd and set it up as part of hardening a box you'll be defending for a while.

▶chkrootkit / rkhunter— rootkit and backdoor scanners
Definition

Scan the system for known rootkit signatures, common backdoor techniques, and suspicious system binary modifications. Not foolproof — signature-based — but a fast first pass.

Use Case (Cyber Defense context)

Quick sanity check on a box you've inherited or suspect is compromised — run early, before you've made other changes that could mask what the scan is looking for.

Syntax
$ chkrootkit
$ rkhunter --check
Notes

Treat a clean scan as a data point, not proof of a clean system — these tools only catch known patterns. Pair with manual review (find for SUID binaries, ps --forest for odd process trees) rather than relying on either alone.

▶ 03 Quick Start & Routine Checks 3 tracks
Three separate tracks: A is read-only recon — safe to run any time, on any box. B and C actively change the system, so they're kept separate from recon and from each other. Run A first. Only move into B or C once you understand what's already there.
▶ A Initial Recon & Routine Checks read-only
Look and understand before you touch anything. Nothing in this track changes the system.
  1. Confirm who you are and what you can do
    Check your own identity, group memberships, and who else has elevated access.
    $ id
$ cat /etc/sudoers
  2. Check the Holy Square of user management
    These four files are the foundation of who can log in and with what access.
    $ less /etc/passwd
$ less /etc/group
$ less /etc/shadow
$ less /etc/sudoers
  3. Enumerate accounts with real login shells
    Surface every account that can actually log in — an unexpected one is a strong compromise indicator.
    $ cat /etc/passwd | grep -E ':(/bin/(bash|sh))$' | awk -F ':' '{print $1}' > users
  4. Review running processes
    Look for anything unfamiliar, oddly named, or running from an unusual path.
    $ ps -ef --forest | less
  5. Check for persistence via cron
    Review both the per-user schedule and the system-wide cron directory.
    $ crontab -e
$ ls /etc/cron.d
  6. Glance at network config and listening ports
    Just looking here — confirm your own IP, then see what's listening and who's connected. Full network setup lives in Track C.
    $ ip a
$ ss -tulnp
$ nmap localhost
  7. Review the current firewall rule set
    See what's currently allowed. Building or changing rules lives in Track B — this step is only about seeing what's already there.
    $ iptables -L --line-numbers
$ ufw status verbose
  8. Spot-check for tampering
    A fast pass for common indicators before deciding what needs deeper investigation.
    $ find / -perm -4000 -type f 2>/dev/null
$ lsattr /etc/ssh/sshd_config
  9. Document everything
    Write down what you found before moving into Track B or C — this is your baseline.
▶ B Firewall Setup & Hardening active — changes the system
Order matters here. Writing the deny policy before your allow rules locks you out. See iptables and ufw/firewall-cmd for full flag references.
  1. Define what actually needs to be reachable
    List the management access you need (e.g. SSH) and the service ports this box legitimately serves, before writing a single rule.
  2. Write allow rules for that list first
    Every port that needs to stay open gets an explicit ACCEPT rule before anything gets blocked.
    # Example: allow SSH and HTTP
$ iptables -A INPUT -p tcp --dport 22 -j ACCEPT
$ iptables -A INPUT -p tcp --dport 80 -j ACCEPT
  3. Allow outbound responses to established connections
    Without this, replies to legitimate outbound traffic get dropped too.
    $ iptables -A OUTPUT -p tcp -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT
  4. Set the default-deny policy last
    Only after steps 2–3 are confirmed in place. This is the step that actually implements implicit deny.
    $ iptables -P INPUT DROP
$ iptables -P OUTPUT DROP
$ iptables -P FORWARD DROP
  5. Verify from a second session before closing your current one
    Open a new connection attempt (a second SSH session, a fresh terminal) to confirm you still have access — don't close the session you're working in until it's confirmed.
  6. Persist the rules so they survive a reboot
    Raw iptables rules are in-memory only by default and vanish on restart. Save them (method varies by distro — e.g. iptables-save, or use ufw/firewalld which persist automatically).
    $ iptables-save > /etc/iptables/rules.v4
  7. Document exactly what's open and why
    Every allowed port, tied to the service that needs it. Makes the next audit — and the next person — much faster.
▶ C Network Setup & Configuration active — changes the system
Which tool manages this varies by distro — see NetworkManager / systemd-networkd / netplan for that variation.
  1. Identify the interface and its current state
    Confirm which interface you're configuring and what it currently has assigned, if anything.
    $ ip a
  2. Assign the intended static IP
    Set the address and subnet mask for this host. Exact syntax depends on the distro's network manager — could be a GUI wired-connection dialog, a netplan YAML file, or nmcli.
    # Example using ip (temporary — won't survive reboot on its own)
$ ip addr add 192.168.1.12/24 dev eth0
  3. Set the default gateway
    Point the host at the router/gateway responsible for traffic leaving the local subnet.
    $ ip route add default via 192.168.1.1
  4. Verify DNS resolution
    Confirm the host can resolve names, not just reach IPs directly.
    $ cat /etc/resolv.conf
  5. Make the change persistent
    Manual ip commands don't survive a reboot. Confirm the change is saved through whichever network manager the distro actually uses.
  6. Confirm it actually applied
    Re-check the interface after applying — don't assume the config took effect just because no error was shown.
    $ ip a
  7. Test connectivity end-to-end
    Ping the gateway, then something beyond it, then confirm DNS-based resolution works too.
    $ ping -c 3 192.168.1.1
  8. Document the IP scheme
    Record what's assigned where — critical for the team when multiple boxes are being configured together.
▶ 04 Reference / Glossary concepts & context
Absolute vs. Relative Path
An absolute path always starts from the filesystem root (/) — e.g. /home/user/Desktop/. A relative path starts from wherever you currently are (pwd) — e.g. var/www/html/. . means the current directory, .. means the parent directory, and ~ means your home directory.
root vs. /root vs. /
root user (UID 0) is the system administrator account. /root is that user's home directory. / is the root of the entire filesystem — the top-level directory everything else lives under. Three different things that share a name.
UID / GID Ranges
User ID 0 is always root. IDs below 1000 are typically reserved for system services. Real human user accounts usually start at UID 1000 and above.
Octal File Permissions
Each permission digit is a sum: read = 4, write = 2, execute = 1. rwx = 4+2+1 = 7. So rwxr--r-- = 744, and r-x-w---x = 755. Three digits total, for owner / group / others.
PAM (Pluggable Authentication Module)
The system-wide framework that governs authentication — login, sudo, SSH, and more all defer to it. Config location differs by distro family (common-auth on Debian, system-auth/password-auth on RHEL).
iptables Chains & Implicit Deny
The 3 core chains are INPUT (incoming), OUTPUT (outgoing), and FORWARD (pass-through) traffic. A firewall following implicit deny blocks everything by default and only allows specific, intentional exceptions — the opposite of blocking a known-bad list.
STDIN / STDOUT / Pipes
STDIN (<) feeds input into a command. STDOUT (>) redirects a command's output into a file. A pipe (|) connects one command's output directly to the next command's input — the building block of most chained one-liners.
Environment Variables
Variables like $PATH that shape how the shell behaves — in this case, which directories it searches (and in what order) when resolving a command name. View them all with env.
Distro Families
Distros cluster into families that share tooling: Debian-based (Debian, Ubuntu — apt), RHEL-based (RHEL, CentOS, Fedora — yum), plus others like Alpine (apk) and Arch (pacman). Knowing the family tells you which command syntax to expect.
Least Privilege
Give every account and process only the access it actually needs to do its job — nothing more. Reduces how much damage any single compromised account or service can do.
The sudo Group
One of the highest-value things to check on any system — who's in it defines who can act as root. An unexpected member is one of the fastest indicators of compromise to check for.
SUID / SGID
Special permission bits that let a file run with the permissions of its owner (SUID) or group (SGID) rather than the user who executed it. Legitimate uses exist (e.g. passwd needs to write to a root-owned file), but an unexpected SUID root binary is one of the most common privilege-escalation footholds — find them with find -perm -4000.
ACL (Access Control List)
A finer-grained permission layer on top of the standard owner/group/others model, letting you grant access to a specific extra user or group. Managed with getfacl/setfacl; shown as a trailing + in ls -l output.
IOC (Indicator of Compromise)
A specific, observable artifact that suggests a system has been compromised — a file hash, an IP address, a filename, a registry-style value, a suspicious process name. Investigations are largely the process of collecting and matching IOCs.
Persistence
Any mechanism an attacker sets up to survive a reboot or maintain access after the initial compromise is cleaned up — a cron job, a modified startup service, an added SSH key, an extra user account. Checking known persistence points (cron, services, authorized_keys, sudoers) is a core part of incident response.
Attack Surface
Everything on a system that's reachable and could potentially be exploited — every open port, running service, and installed package adds to it. Hardening is largely the process of shrinking this: disabling what isn't needed.
Anti-Forensics
Techniques used to hide evidence of an intrusion — clearing shell history, touching timestamps to disguise when a file was really modified, deleting or tampering with logs. Their presence (e.g. a suspiciously empty history file) can itself be a signal something happened.
/var/log vs. the systemd Journal
Two overlapping logging systems exist on most modern distros: traditional plaintext files under /var/log, and the binary systemd journal read with journalctl. Depending on the distro's configuration, one, the other, or both may hold the events you're looking for — check both if something seems to be missing.
CIDR Notation & Subnet Mask
Two ways of expressing the same thing: how many bits of an IP address identify the network vs. the individual host. 192.168.1.12/24 means the first 24 bits are the network portion — equivalent to a subnet mask of 255.255.255.0. A smaller number after the slash (e.g. /16) means a larger network with more possible hosts.
Default Gateway
The router a host sends traffic to when the destination isn't on its local subnet — effectively "the way out." Set with ip route add default via. Get this wrong and the host can talk to local devices but nothing beyond them.
DNS & /etc/resolv.conf
DNS resolves human-readable names (like a hostname) to IP addresses. On Linux, which DNS server(s) a host queries is typically listed in /etc/resolv.conf — worth checking directly if name resolution isn't working even though raw IP connectivity is fine.
Connection Tracking & Stateful Firewalls
A stateful firewall remembers which connections it already allowed, so it can automatically permit the return traffic without a separate rule for it. This is what --ctstate ESTABLISHED,RELATED refers to in iptables rules — "let responses to traffic we already approved back in."
SYN Cookies
A kernel-level defense against SYN-flood denial-of-service attacks, where an attacker opens huge numbers of half-finished connections to exhaust a server's resources. Enabling SYN cookies (sysctl) lets the kernel handle those connection attempts without committing resources until they're confirmed legitimate.
